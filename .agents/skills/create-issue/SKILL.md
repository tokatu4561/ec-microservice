# GitHub Issueの作成

Issueには「何を、なぜ、どこまで実現するか」を残す。実装の手順書にはしない。

## 内容をまとめる

- ユーザーの依頼と必要な既存コード・仕様を確認し、目的と観測可能な受入条件をまとめる。
- 振る舞いや範囲に影響する不明点だけ質問する。小さな実装上の選択は実装時に任せる。
- タイトルは解決したい問題または実現したい動作を短く表す。本文はユーザーの言語に合わせる。
- 明示されたAPI互換性、データ移行、サービス間契約などの制約は省略しない。クラス名・関数名・変更ファイル一覧・疑似コードは、ユーザーの指定や合意済みの必須制約でない限り追加しない。
- 本文を作成・下書きするときは、[本文テンプレート](references/issue-template.md)を読み、その形式に沿ってまとめる。

## GitHubへ作成する

- 作成先はユーザー指定を優先し、なければこのリポジトリのGit remoteから特定する。複数候補で特定できなければ確認する。作成前に同じ要望の既存Issueを確認し、既存で足りる場合はそのURLを返す。
- 利用可能なGitHubコネクタ、または認証済みの `gh` を使う。CLIでは作成先を `--repo OWNER/REPO` で指定し、本文は一時ファイルに書いて `--body-file` で渡す。
- 「Issueを作成して」という依頼は投稿の承認として扱い、内容と対象が明確なら追加確認を挟まない。「下書き」「相談」の依頼では本文を提示するだけで投稿しない。スキルを用意する依頼だけではIssueを投稿しない。
- 指定のない担当者・ラベル・マイルストーンは追加しない。
- 作成結果のURLを確認して返す。投稿結果が不明なら既存Issueを確認してから対応し、重複作成につながる再試行をしない。認証・権限・接続で作成できなければ、本文と未作成の理由を返す。

## 記録の分担

Issue本文は要件、必要な作業コメントは引継ぎ、PR本文は実際の変更と検証結果、ADRは長期的な設計判断を扱う。
作業中の修正回数や検証ログを初期Issue本文に詰め込まない。ローカルの計画ファイルや別のテンプレートは作らない。
