## 背景と制約

[Issue #4](https://github.com/tokatu4561/ec-microservice/issues/4)では、サービス分割の利点と分散特有の課題を小さな単位で学ぶ。
2026-09-16の会話でPayment＋同期HTTPを選択し、最初の単位はPayment単体までと合意した。
ユーザーは、分割が実務のどの課題に対応するのかを確認したうえで実装を承認した。
現在のシステムで、複数チームの調整や独立スケールが必要な性能問題を確認したわけではない。
目的は、決済を別の単位で変更・起動・停止し、決済記録の更新責任を分ける構造を体験すること。

実決済・認証・本番公開は対象外。既存注文への接続、通信タイムアウトや部分成功の実験、
Saga・Outbox・汎用冪等性・自動再送は次の単位以降で扱う。
既存注文は引き続きADR 0003・0004の単一DBトランザクションと従来の模擬決済を利用し、今回それを置き換えない。

## 採用する判断

- `payment/` に既存と同じGo・pgxの版を使う独立アプリを置き、同期HTTPで模擬決済作成・照会・取消を公開する。Next.jsと既存Goアプリは今回接続しない。
- Payment専用PostgreSQL、接続情報、永続ボリュームを用意する。DBは専用の内部ネットワークに置き、DBポートをホストへ公開しない。Payment APIは127.0.0.1:8081を既定とする。
- 決済データの所有者をPaymentに限定し、既存DBの参照・更新は実装しない。注文IDは既存と同じ形式を用いるが、別DBの注文への外部キー・存在照会は設けない。
- 注文IDを主キーとして、同じ注文IDの決済作成は409で拒否する。再送へ元の成功応答を返す汎用的な冪等性APIは導入しない。
- 決済は`succeeded`または`failed`で保存し、`succeeded`から`cancelled`へ取消できる。取消を行ロックで直列化し、再取消は日時を含む同じ結果を返す。
- 初回スキーマを埋め込みSQLで起動時に作成する。今回の単体学習でテーブルを用意する最小構成として選ぶ。`CREATE TABLE IF NOT EXISTS`は既存テーブルの変更管理を担わないため、今後のスキーマ変更には別の移行処理を用意する。
- `service`・`request_id`・`order_id`・結果をJSONログに出し、受け取った有効な`X-Request-ID`を応答に引き継ぐ。現段階ではPayment内の相関であり、サービス横断追跡は注文連携時に検証する。

## 比較案と見送った理由

- Inventoryを先に分割：学習2の在庫ロックとの比較に向くが、商品一覧・カートへの影響が大きい。少ない変更範囲で別DBと通信の境界を確認できるPaymentを選んだ。
- 同じアプリ内のモジュール分離だけを行う：責務整理には有効だが、独立した起動停止と通信障害を学ぶ今回の目的には、別プロセスが必要。
- 非同期イベントを最初から導入：キューと配送状態の管理も同時に必要になるため、まず呼び出しと応答を追いやすい同期HTTPにする。
- 最初から注文に接続：分散トランザクションの状態設計まで同時に必要となるため、ユーザーが選んだPayment単体の区切りで質疑を行う。
- 既存DBに決済テーブルを追加：今回学ぶデータの所有境界・独立DBの運用を明確にするため、専用DBを選んだ。

## 利点と不利益

Paymentだけをビルド・再起動・停止でき、決済記録の変更をAPIへ集約できる。
一方、DB・コンテナ・ヘルスチェック・ログ・テストの運用対象が増える。
現段階では新サービスと従来の模擬決済が併存し、画面からの注文は新サービスを使わない。

注文接続後は、決済成功後の注文保存失敗や応答喪失、取消通信失敗が起こり得る。
同期HTTPによる依存先の遅延・停止も注文側へ影響するため、分割だけで障害分離が完成するわけではない。
今回のPayment単体でも、DB書き込み応答の喪失時に結果が不明になる可能性があり、自動再送せず注文IDで照会する。
実際の外部課金・返金の安全性、分散整合性、本番の処理能力は今回の検証範囲外。

## 見直す条件

- OrderからPaymentを呼ぶ次単位で、注文状態、タイムアウト、取消結果不明、再送と照合の契約を具体化する。
- 決済の複数試行や実際の外部決済を扱う場合、注文ID主キーの重複拒否で十分かを見直す。
- スキーマ更新や複数レプリカを扱う場合、移行の履歴・起動時競合・DB権限を設計する。
- ローカル学習以外へ公開する場合、認証・秘密情報管理・ネットワーク境界を再設計する。
