# 0004: 匿名カートをDBに保存し複数商品を一括確定する

状態: 提案
日付: 2026-09-12
関連ADR: [0003: 注文と模擬処理を同一DBトランザクションで確定する](0003-monolith-order-transaction.md)
人の採用記録: 実装計画は会話で承認済み。本ADRの採用は未確認。

## 背景と制約

学習者からカートと複数商品の注文が要望され、DB保存の匿名カートから1つの注文IDでまとめる計画が承認された。
1商品でも在庫不足なら全体を不成立にし、失敗履歴とカートを保存する。
認証・別端末共有・実決済・部分成立・分割配送・汎用的な冪等性キーは追加しない。
既存の単品注文と未コミットの学習1実装を保持する。

## 採用する判断

- `carts`と`cart_items`で購入予定を保存する。256ビットのランダムな匿名トークンをHttpOnly・SameSite=LaxのCookieに置き、DBにはSHA-256ハッシュを保存する。作成から30日で失効する。期限切れ行の削除ジョブは設けない。
- 同一商品は1明細にまとめる。PUTは絶対数量とし、画面の追加操作が現在数量に加算した値を送る。更新と注文は必須のバージョンを送り、カート行ロック取得後に比較する。古い版は409として再取得する。
- `orders`は注文全体・決済・配送の状態、`order_items`は当時の商品名・単価・数量を持つ。旧注文を同じIDの1明細へ移行する。旧POSTの単品入力は受け付け、応答は`items`へ統一する。
- カート追加時には在庫を確保せず、表示額は現在価格による見積とする。checkoutでカート行、その後商品ID昇順に商品行をロックする。逆順の注文でも同じ順に取得して循環待ちを避ける。
- 同一Read Committedトランザクションで全在庫確認・確保・模擬処理・注文全明細保存を行う。不足時は在庫を変更せず、模擬失敗時は全確保分を戻す。配送失敗時の模擬決済取消を継続する。
- 成功時だけカートを空にする。業務失敗でも処理済みの版としてバージョンを進め、同じ版の再送を拒否する。`last_order_id`で直近の結果を照会できるようにする。
- DB途中エラーはカートも含め全体をロールバックする。画面は送信中に編集・再送を無効化し、通信エラー時に自動注文再送しない。

## 比較案と見送った理由

- ブラウザー内だけのカート: DB保存という合意要件を満たさず、サーバー側でカートの競合を扱えない。
- 会員アカウント: 匿名で同じブラウザーから再利用する今回の範囲を超える。
- 商品ごとに別注文を作る: 1つの注文IDと全商品一体の成功・失敗という合意に合わない。
- 商品指定順でロックする: 逆順の注文同士が互いのロックを待つ可能性がある。
- カート追加時の予約: 放置カートの在庫解放が必要になり、注文確定時に確保する合意と異なる。
- 汎用的な冪等性キー: 今回はカートの版による重複成功防止に範囲を限定する。旧単品APIへの手動再送は別注文になる。

## 利点と不利益

複数商品の全体整合性と失敗履歴を単一DBで学べる。注文明細は価格改定後にも当時の情報を保持する。
同じカート・人気商品への処理は直列化される。カートは最大100商品、金額はJavaScriptの安全な整数範囲に制限する。
期限切れデータはDBに残る。Cookieを失うと以前のカートに戻れない。
COMMIT応答やHTTP応答の喪失で結果が不明になる場合は、再取得した直近注文やログで確認する。
外部決済の返金や配送取消をDBロールバックで実現できるという設計ではない。

## 見直す条件

会員・複数端末・予約在庫・部分成立・実決済・サービス分割を導入する際に、所有権・トランザクション境界・冪等性・補償を再設計する。
競合負荷の比較、期限切れデータ削除、マイグレーション履歴管理は必要になった段階で検討する。
