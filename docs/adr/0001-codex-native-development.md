# 0001: Codex標準機能と指示で開発を進める

状態: 提案
日付: 2026-09-10
関連ADR: なし
人の採用記録: 方針は会話で確認済み。文書の最終確認待ち。

## 背景と制約

目的はECの設計・実装を学ぶこと。開発補助プログラムの保守負担は最小限にしたい。
ユーザーは時間による強制終了を不要とし、修正回数をモデルへの指示で管理する方針を示した。

## 採用する判断

計画・実装・検証・レビューにはCodexの標準機能を使う。
修正最大2回、未解決時は人に戻すというルールをAGENTS.mdでモデルに指示する。
目的・受入条件はGitHub Issue、細かな実装検討と修正回数は会話、必要な引継ぎはIssueコメント、変更と検証結果はPRに残す。
親がIssueの要件と最新の検証結果をreviewerへ渡し、ローカルの計画ファイルは持たない。
Issueはcreate-issueスキルの最小テンプレートで作り、実装手順書にはしない。
重要なwhyだけをADRに整理し、独自の実行・状態管理プログラムは持たない。
レビュー担当1人をプロジェクトの標準TOMLで定義し、親が実装・検証後に委任して結果を回収する。
テスト作成・実行は親が担当し、レビュー担当はテスト不足を含む読み取り中心の確認に限定する。

## 比較案と見送った理由

- 自作Python制御: 回数・時間を強制できるが、CLI互換性、状態管理、プロセス終了、専用テストの保守が増える。強制終了が不要となったため採用しない。
- フックや別言語のスクリプト: 実装手段を変えても独自の制御と保守は残るため追加しない。
- 指示と標準操作: 機械的な強制はないが、人が確認する現在の開発に必要な手順を少ない構成で運用できる。
- 手動の別タスクへの受け渡し: コピーと再依頼の手間を避けるため、標準サブエージェントでの委任に変更する。
- テスト・設計など多数の専用エージェント: 現時点では親とreviewerで分担できるため、必要性が出るまで増やさない。
- ローカル計画ファイルとIssueの併用: 要件や進捗が二重管理になるため、Issue運用への移行に合わせて廃止する。

## 利点と不利益

開発補助のコード保守が不要になり、運用ルールと小さな標準設定だけを管理する。
一方、回数の遵守と記録の正確さはモデルの指示追従に依存する。
レビューの受け渡しは親が標準機能で行い、人がIssueの要件と結果を確認する。
Issueへの記録・取得にはGitHub接続が必要になる。利用できない場合は会話の要件と引継ぎを明示し、ローカル計画を再導入しない。
サブエージェントの利用可能性と設定仕様には依存し、利用できない場合はレビュー未実施として報告する。

## 見直す条件

実際の運用で反復超過・記録漏れが頻発する、または無人実行や機械的な停止保証が必要になった場合。
作成済みの仕組みがあることだけを理由に自動化を維持しない。
