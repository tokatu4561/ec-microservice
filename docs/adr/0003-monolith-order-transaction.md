# 0003: 注文と模擬処理を同一DBトランザクションで確定する

状態: 提案
日付: 2026-09-12
関連ADR: [0002: 商品一覧をGo・Next.js・PostgreSQLで構築する](0002-local-product-catalog.md)
人の採用記録: 実装計画は会話で合意済み。本ADRの採用は未確認。

## 背景と制約

[Issue #2](https://github.com/tokatu4561/ec-microservice/issues/2)の学習1で、商品一覧に注文・在庫・模擬決済・模擬配送を追加する。
学習者は、在庫不足や模擬処理の失敗時に失敗注文を保存し、在庫を注文前の値に戻す方針を選択した。
配送失敗時は模擬決済も取り消す計画が承認されている。実決済・実配送・分散トランザクションは対象外。
商品データを持つ既存DBを破棄せず、注文テーブルを追加する必要がある。

## 採用する判断

- Goの注文処理で`BEGIN`し、`SELECT ... FOR UPDATE`で商品行をロックする。READ COMMITTEDの同一トランザクションで在庫確認・確保・模擬処理・注文保存を行う。同じ商品への注文を直列化して売り越しを防ぐ。
- 正常時は在庫を減らし、注文を`shipping_requested`としてコミットする。模擬決済は`succeeded`、模擬配送は`requested`とする。
- 在庫不足では在庫を変更せず、模擬処理を実施しない。模擬決済・配送失敗では同じトランザクション内で確保分の在庫を戻す。失敗注文は`failed`と理由を保存してコミットする。
- 配送失敗では模擬決済を`cancelled`、模擬配送を`failed`とする。外部呼出しはなく、DB内の状態だけを変更する。
- DBエラー時は注文と在庫をロールバックする。リクエストの期限切れ後にも後始末できるよう、ロールバックには独立した短い期限を与える。
- 注文には商品IDに加えて注文時の名称・単価を保存する。後の商品改定が過去の注文表示に影響しないようにする。
- 保存した失敗注文もPOSTでは201を返し、業務結果は`status`と`failureReason`で表現する。未保存の入力エラーやシステムエラーとは区別する。
- 注文テーブルは再実行可能な追加SQLで作成する。Composeの`migrate`が正常終了してからAPIを起動し、既存の商品・注文データを維持する。

## 比較案と見送った理由

- 業務失敗でも全体をロールバックして履歴を残さない：学習者が選択した失敗履歴保存の方針を満たさない。
- 在庫確認と在庫更新を別トランザクションで行う：並行注文が同じ在庫を見て確保する可能性がある。
- 楽観ロック：今回は行ロックで整合性を確保する最小の実装とし、方式比較・競合時の再試行は学習2で扱う。
- 配送失敗を決済済み・在庫確保済みのまま残す：学習1では配送の再試行を追加せず、承認済みの在庫復元・模擬決済取消の方針を使用する。
- Saga・Outbox・外部サービス連携：単一DBのトランザクションを学ぶ段階なので導入しない。

## 利点と不利益

業務上の失敗とDB障害の違いを、注文・在庫・ログで比較できる。トランザクション途中のSQL失敗でも部分更新を残さない。
一方、同じ商品への処理はロック待ちになり、処理が長くなるほど並行性が下がる。
実際の外部決済を同じ方法で取り消せるわけではない。模擬状態の取消と実返金は区別する。

COMMIT応答やHTTP応答の喪失では、呼出側が保存結果を確定できない場合がある。
自動再送はせず、利用可能なら注文IDで照会する。冪等性キーは今回実装しないため、手動の再送は別注文になる。
現在の追加SQLは既存の注文テーブルの定義変更を行わない。将来の変更には別マイグレーションを追加する。

## 見直す条件

学習2で競合・負荷・キャンセルを検証する際にロック方式と処理期限を比較する。
サービス分割で別DBや実際の外部副作用を扱う際には、トランザクション境界、再試行、冪等性、補償を再設計する。
スキーマ変更が増えた時点でマイグレーションの履歴管理方法を検討する。
