# 0005: 複数商品注文のSQLを一括化し、独立した負荷試験で比較する

関連ADR: [0003: 注文と模擬処理を同一DBトランザクションで確定する](0003-monolith-order-transaction.md)、[0004: DB保存カートと複数明細の一括注文](0004-persistent-cart-multi-item-checkout.md)

## 背景と制約

[Issue #3](https://github.com/tokatu4561/ec-microservice/issues/3)の学習2で、同時注文と接続プールについて質疑した後、学習者は楽観ロックの比較を後回しにし、負荷試験・原因の切り分け・改善前後の比較を先に進める方針を選択した。
負荷を実行するだけでは学びにならなかったため、変更前の負荷、待機とクエリの解析、変更の確認、変更後の再実行を本人が順に体験できる手順も求められた。

現行の成功注文は、N商品に対して商品取得N回・在庫更新N回・明細保存N回・注文保存1回を行う。
在庫と注文の整合性、ID順の行ロック、同一トランザクション、模擬失敗時の在庫復元を維持する。
通常のEC用DBを初期化せず、ローカルで再実行可能にする。サービス分割・受付制限・外部APIの遅延とキャンセルは今回の実装範囲に含めない。

## 採用する判断

- `createOrderTx`の商品取得を`ANY(...) ORDER BY id FOR UPDATE`にまとめ、全商品をID順にロックする。先にID・数量・重複を検証し、取得できなかった商品があれば処理を失敗にする。
- 在庫更新と明細保存を、それぞれ配列と`unnest`による1回のSQLへまとめる。配列の位置と商品ID・数量・価格・不足フラグの対応を保持する。トランザクションの境界は変更しない。
- 基準コミット`1c11b6138126f154e089689dcb06983e14917fb7`の注文関数をテスト専用の比較実装として保持する。通常の単品・カート注文には新しい実装を使用する。
- 負荷用HTTPサーバーと比較実装を`_test.go`に置き、専用Dockerターゲットで実行する。通常APIに実験用の入口を追加しない。測定時は注文の共通処理を直接呼び、UI・カート編集・Cookie処理を計測区間に含めない。
- 専用Composeプロジェクト・DB名・tmpfsを使う。各条件の前にDBコンテナを作り直し、WALや資源状態の持ち越しを避ける。API・DB・k6の資源条件を両方式で揃える。
- k6でHTTP応答とGoの取得・SQLトレースを記録し、別途プール状態・DB待機・コンテナCPU/メモリ・SQL統計・代表クエリの実行計画を採取する。ロック取得SQLの所要時間を純粋なロック待ち時間とは扱わない。
- 学習の主手順はk6の直接実行とpsqlによる段階的な解析・照合にする。k6が人向け集計と照合用件数を出力し、DB照合はSQLで行う。既存Python一括実行は任意の補助として残す。
- 性能しきい値未達は結果として保存する。一方、応答のチェック失敗・欠落、在庫や注文のDB照合不一致は正しさの失敗にする。

## 比較案と見送った理由

- プール上限やアプリ数を増やす：同じ商品をロックする待機が観測され、DBのCPUには余裕があった。まずロック保持中のSQL処理を短縮する。
- インデックスを追加する：代表の商品取得計画では既存の主キーインデックスを利用していた。新規インデックスが必要という根拠は得られていない。
- SQLを個別のままパイプライン化する：往復を減らせる可能性はあるが、今回は最大100明細という範囲でSQL自体をまとめる方法を比較する。
- 決済処理をコミット後へ移す：実際の決済では状態遷移と補償を別途設計する必要がある。今回のSQL改善では境界を変更しない。
- 通常のカート操作を毎注文20回繰り返す負荷：カート編集の負荷が混ざるため、今回の共通注文処理の比較からは分ける。今回の数値をEC画面全体の性能とは主張しない。

- Pythonで全段階を自動実行する手順を主にする：学習者から処理が見にくいとの指摘があり、k6とSQLを自分で実行して読む手順へ変更した。k6だけへDB管理まで集約せず、Docker・psqlの役割を分ける。

## 利点と不利益

20明細の成功注文でSQL呼び出しはBEGIN・COMMITを含め63回から6回になった。
標準の20 VUでは約212→333注文/秒、平均接続取得時間46.79→29.77ms、p95 161.84→139.45msだった。
全8条件でシステムエラー率0・在庫不足0、66,038注文の応答とDBを照合して成功した。

一方、5・10 VUではp95/p99が悪化した。追加の別商品群条件でも全面的な裾のレイテンシ改善は確認していない。
遅い側の個別リクエストが生じた詳細原因は未確認。スループットの改善と、すべての応答時間の改善は区別する。
一括SQLでは配列の対応と行ロック順が重要となり、単純な商品ごとの処理より注意点が増える。
比較用の旧実装はスナップショットとして保持するため、将来の仕様変更後も現行仕様と同等であるとは限らない。

固定VU数の閉じた負荷モデル、各条件1回・30秒、同一PCのDocker VM、tmpfsという条件である。
本番処理能力、一定到着率での過負荷耐性、継続的なメモリ安定性を証明するものではない。

手動手順は途中で結果を読みやすい一方、DB再作成・出力先切り替え・観測・後片付けを利用者が行う必要がある。観測結果の自動保存や同時実験の排他制御は行わず、同時実行しないことと条件ごとの再初期化を手順に明記する。

## 見直す条件

- p95/p99の悪化を抑える必要がある、または実際の許容値を超える場合は、個別リクエストの待機・SQL・DB資源を追加計測する。
- 実際のデータ量・商品分布・到着率・永続ディスク条件を扱うときは、新しい試験条件を事前に合意して評価する。
- 注文の仕様やスキーマを変更したら、比較用スナップショットの用途を確認する。
- 外部決済やサービス分割を導入するときは、状態遷移と補償を含む別の設計判断を行う。
